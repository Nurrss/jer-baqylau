# Архитектурные решения (ADR)

Короткие записи: контекст → решение → последствия. Новые решения добавляются в конец.

---

### ADR-001. Один процесс: API + бот + планировщик
**Контекст.** Бот с FSM и загрузкой файлов плохо подходит для serverless, а два сервиса удваивают деплой.
**Решение.** FastAPI, aiogram 3 (вебхук `POST /tg/webhook`) и APScheduler живут в одном контейнере на Railway. Бот вызывает сервисный слой напрямую, без HTTP-запросов к самому себе.
**Последствия.** Один деплой, общая транзакционная логика. Горизонтальное масштабирование возможно: вебхук идемпотентен, планировщик защищён advisory lock (ADR-008).

### ADR-002. Подключение к Supabase — через Session pooler
**Контекст.** Прямой хост `db.<ref>.supabase.co` доступен только по IPv6. Transaction pooler (6543) ломает prepared statements в asyncpg.
**Решение.** `DATABASE_URL` указывает на Supavisor **session** pooler (`:5432`, `sslmode=require`). SSL включается автоматически, если в URL есть `supabase` или `sslmode=require`.
**Последствия.** Работает с Railway и из домашних сетей без IPv6. Код не знает, Supabase это или локальный PostGIS.

### ADR-003. Разработка без облака до получения ключей
**Контекст.** Ключей Supabase пока нет, а работа не должна стоять.
**Решение.** Все внешние зависимости спрятаны за адаптерами и переключаются через `.env`:
- `AUTH_MODE=local|supabase`: локально API выдаёт HS256-JWT по демо-логину (`/api/v1/auth/login` работает только в local), на проде проверяется JWT Supabase (JWKS или legacy HS256).
- `STORAGE_BACKEND=local|supabase`: локальный диск с HMAC-подписанными ссылками `/files/...`, либо приватный бакет Supabase с signed URLs.
- Realtime: если нет `VITE_SUPABASE_URL`, фронт опрашивает `/api/v1/events?since=` каждые 5 с.

**Последствия.** Переход на облако — это изменение `.env` без правок кода. В production `AUTH_MODE=local` запрещён валидатором настроек.

### ADR-004. Мультиархитектурный образ PostGIS
**Контекст.** `postgis/postgis` публикуется только для amd64, на Apple Silicon он работает через эмуляцию.
**Решение.** Используем `imresamu/postgis:15-3.4`: это сборка того же мейнтейнера для amd64 и arm64. Образ переопределяется через `POSTGIS_IMAGE`.

### ADR-005. Enum'ы — VARCHAR + CHECK, а не нативные PG enum
Добавление значения — обычная миграция без `ALTER TYPE`. Значения совпадают со строками API.

### ADR-006. Машина состояний и расширения к ТЗ
Все переходы описаны в `app/domain/state_machine.py`; недопустимый переход возвращает `409 INVALID_TRANSITION` со списком допустимых статусов. Дополнения к ТЗ:
- `RESOLVED → UNDER_CHECK | VIOLATION`: повторное нарушение на ранее исправленном участке.
- `RETURNED_TO_STATE` — терминальный статус; при переходе в него `owner_type` становится `STATE`.
- `→ VIOLATION` требует `violation_type`. Если дедлайн не задан, ставится +30 дней.
- `→ OK` очищает тип нарушения и дедлайн.
- Сигнал `CONFIRMED` автоматически переводит участок в `VIOLATION` (тип берётся из категории сигнала). Сигнал `REJECTED` возвращает участок `UNDER_CHECK → OK`, если открытых сигналов на нём не осталось.
- Решение по корневому сигналу каскадом применяется к его открытым дубликатам, чтобы каждый житель получил ответ.

### ADR-007. Уведомления — строго после коммита
Сервисы регистрируют отправку через `outbox.after_commit`. При откате транзакции сообщения не уходят. Когда участок меняет статус как побочный эффект перехода сигнала, отдельное уведомление по участку не шлётся: житель уже получает сообщение о своём сигнале.

### ADR-008. Конкурентность и идемпотентность
- Сид и `demo-reset` выполняются под `pg_advisory_xact_lock`, спутниковый скан — под `pg_try_advisory_xact_lock`.
- Изменения статусов идут через `SELECT … FOR UPDATE`.
- События `events` не сбрасывают свой id при `demo-reset`: клиенты, которые опрашивают API, не «откатываются» назад.

### ADR-009. Детерминированные UUID сид-данных
UUID участков, заявлений и сигналов из сида — это `uuid5` от кадастрового номера или трек-номера. После `demo-reset` подписки жителей в боте продолжают указывать на те же заявления.

### ADR-010. Генерация участков
Участки квартала строятся из общей сетки вершин со случайным сдвигом, поэтому соседи стыкуются без щелей и наложений. Затем квартал поворачивается целиком. Миллиметровые наложения из-за округления координат вычищаются вычитанием уже принятых соседей. Тест проверяет `ST_IsValid` и отсутствие наложений больше 0,01 м². Кадастровые номера берутся из фиктивного диапазона кварталов `06:097:9xx:nnn`.

### ADR-011. Фото
Pillow поворачивает снимок по EXIF, удаляет метаданные и сохраняет JPEG (сторона до 2048 px) и превью (480 px). GPS и время съёмки извлекаются из EXIF до удаления метаданных. Координаты фото хранятся в PostGIS (`photos.location`), как требует §12 ТЗ.

### ADR-012. Хранение языка и текстов
Бот и уведомления используют Fluent (`apps/api/app/locales/{ru,kk}/*.ftl`). Тест проверяет, что наборы ключей RU и KK совпадают. Веб использует i18next, нормативный контент лежит в `packages/seed/knowledge/{ru,kk}`.

### ADR-013. Цепочка хешей вместо внешнего блокчейна
Журнал статусов связан цепочкой SHA-256 внутри Postgres: запись хранит `prev_hash` и `hash`, вставка сериализуется `pg_advisory_xact_lock(724003)`. Этого достаточно, чтобы обнаружить правку и удаление задним числом. Голова цепочки печатается в акте и публикуется на странице проверки. Для продакшена голову можно раз в сутки подписывать ЭЦП организации или публиковать вовне. Внешний блокчейн не нужен.

### ADR-014. Фотоотчёт владельца — веб-страница, а не приложение
Ссылка открывается на любом телефоне без установки и входа. Снимки берутся только из потока камеры (`getUserMedia` → canvas), поэтому EXIF в них нет: проверка `EXIF_GPS` в этом случае `skip`, а место подтверждает геолокация браузера. Вердикт антифрода владельцу не сообщается, чтобы нельзя было подбирать обход. Пока отчёт не рассмотрен, новый запрос по участку не создаётся.

### ADR-015. Доказательство для «Устранено»
Сервер отказывает в `RESOLVED` без доказательства (`422 EVIDENCE_REQUIRED`), UI показывает список и блокирует кнопку. Учитываются только материалы после выдачи предписания (последний переход в `IN_REMEDIATION`/`VIOLATION`).

### ADR-016. Ограничение памяти GDAL
Контейнер видит всю память хоста, и блочный кеш GDAL по умолчанию (5 % от неё) вместе с параллельным чтением COG приводил к OOM-рестартам на Railway. Решение: `GDAL_CACHEMAX=32` МБ, `VSI_CACHE_SIZE=10` МБ на файл, не больше одной задачи истории одновременно, 1 поток чтения (API в покое ~400 МБ, лимит 512 МБ; каждый поток +45 МБ), попытка фиксируется в Redis на 30 минут и переживает рестарт, повтор задачи для участка не чаще раза в 30 минут. Скан и задачи истории делят один семафор `RASTER_SLOT` и никогда не идут одновременно; на Railway задан `MALLOC_ARENA_MAX=2`, чтобы память потоков возвращалась системе.

## Требует сверки

- **Нормативка и процедуры** в `packages/seed/knowledge/*` составлены по общедоступным описаниям услуг egov.kz и Земельному кодексу РК. Номера статей не указываются, если нет уверенности. **Требует сверки с актуальным регламентом.**
- **Казахские тексты** (локали бота, веба, сид-данные) **требуют вычитки носителем языка.**
- **Данные** — участки, заявления, сигналы и имена — полностью вымышлены. Координаты правдоподобные, окрестности Тараза.
