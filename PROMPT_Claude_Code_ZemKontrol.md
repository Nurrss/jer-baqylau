# ПРОМПТ ДЛЯ CLAUDE CODE — «ЖерБақылау»: цифровой мониторинг земель + сервис для граждан

> Скопируй всё ниже линии в Claude Code целиком (в пустой папке, которая станет git-репозиторием).
> Команда: 2 человека (Windows + macOS), каждый со своим Claude Code. Деплой: Vercel + Supabase + Railway. Языки: русский + казахский.

## 0. Роль и цель

Ты — ведущий full-stack инженер и техлид команды на хакатоне. Строим **production-grade MVP** двустороннего сервиса мониторинга земель, **задеплоенный в интернет**:
1. **Веб-панель инспектора** — GIS-карта участков, фотофиксация нарушений, дедлайны, жизненный цикл.
2. **Telegram-бот для граждан** — статус заявлений, база знаний, «Народный контроль» с геолокацией и фото.

Критерии жюри и как мы их закрываем:
| Критерий | Вес | Что значит для нас |
|---|---|---|
| Работоспособность End-to-End | 35% | Житель отправил фото+гео в бот → точка **мгновенно** появилась на карте инспектора → инспектор сменил статус → **житель получил уведомление в боте**. Всё — на публичных URL. |
| UX/UI | 25% | Карта интуитивна для госслужащего; в боте только кнопки; полная поддержка RU/KZ |
| Техническая реализация | 20% | Стабильность, настоящая пространственная БД (PostGIS), корректная геопривязка |
| Потенциал масштабирования | 20% | Адаптеры под госкадастр (ГБД ЗКС / egov) и спутниковый мониторинг (Sentinel-2 / NDVI) |

Никаких заглушек в пользовательских сценариях — всё, что видит жюри, должно реально работать на проде.

## 2. Архитектура, стек и деплой

```
 Telegram ──webhook──► ┌──────────────────────────────┐
                       │ Railway: API + Bot (1 сервис) │
 Vercel: Web (React) ─►│ FastAPI + aiogram 3 (webhook) │
   ▲    REST (JWT)     │ APScheduler (спутник. скан)   │
   │                   └──────┬───────────────┬───────┘
   │ Realtime                 │ SQL            │ Storage API
   │ (postgres_changes)       ▼                ▼
   └──────────────── Supabase: Postgres 15 + PostGIS, Auth, Storage, Realtime
                       Upstash Redis — FSM-хранилище бота
```

**Почему так:** Vercel — только для статического фронтенда (serverless не подходит для бота с FSM и загрузкой файлов). Supabase закрывает БД с PostGIS, хранение фото, вход инспектора и realtime без своего WebSocket-сервера. Railway держит постоянный контейнер без «засыпания» (в отличие от бесплатного Render — это важно, чтобы бот не тормозил на демо).

**Backend (`apps/api`):** Python 3.12, uv, FastAPI, SQLAlchemy 2 (async) + GeoAlchemy2 + asyncpg, Alembic, Pydantic v2, Shapely, httpx. Проверка JWT Supabase (JWKS / JWT secret) для запросов инспектора; сервисный ключ для внутренних вызовов.
**Bot:** aiogram 3, **в том же процессе, что и API**: webhook-роут `POST /tg/webhook` с проверкой `X-Telegram-Bot-Api-Secret-Token`. Локально — режим long polling (переменная `BOT_MODE=polling|webhook`). FSM-хранилище — `RedisStorage` на Upstash (`rediss://`). Бот работает с БД через тот же сервисный слой, что и API (без HTTP-прыжков внутри процесса).
**Frontend (`apps/web`):** React 18 + TypeScript + Vite, MapLibre GL (`react-map-gl/maplibre`), TailwindCSS + shadcn/ui, TanStack Query, Zustand, `@supabase/supabase-js` (только Auth + Realtime), i18next (ru/kk), date-fns, lucide-react. Подложки: OSM и спутник (Esri World Imagery) с переключателем. `vercel.json` с SPA-rewrites.
**Хранилище фото:** Supabase Storage, приватный бакет, отдача через signed URLs; превью генерировать на бэкенде (Pillow), EXIF-координаты извлекать.
**Realtime:** бэкенд пишет события в таблицу `events` (и меняет `signals`/`parcels`) → фронтенд подписан на `postgres_changes` через Supabase Realtime. RLS: чтение только для `authenticated` (инспектор), запись — только через бэкенд (service role).
**Локальная разработка:** `docker compose` с `postgis/postgis` + `redis` + api — чтобы оба разработчика работали без облака и не мешали друг другу. Либо подключение к отдельному dev-проекту Supabase. Код не должен зависеть от того, где БД (только `DATABASE_URL`). Для локального realtime допустим fallback: поллинг каждые 5 с, если Supabase Realtime не настроен.

**Структура монорепо:**
```
apps/api  (FastAPI + bot + scheduler)   apps/web (React)
packages/seed (GeoJSON, заявления, контент)
docs/ (PLAN, DECISIONS, ARCHITECTURE, API, DEPLOY, DEMO_SCRIPT)
supabase/ (SQL: extensions, RLS-политики, бакеты)
docker-compose.yml  Makefile  .env.example  .gitattributes  README.md  CLAUDE.md
```

**Деплой (сделай `docs/DEPLOY.md` — пошагово, для человека, который делает это первый раз):**
1. Supabase: создать проект (регион ближе к Казахстану, напр. Frankfurt), включить `postgis`, применить миграции Alembic и `supabase/*.sql` (RLS, Realtime publication для `events`, `signals`, `parcels`, бакет `photos`), создать пользователя-инспектора в Auth.
2. Upstash: Redis-база, получить `REDIS_URL`.
3. Railway: сервис из `apps/api/Dockerfile`, переменные окружения, healthcheck `/health`, при старте — миграции и идемпотентный сид. После деплоя скрипт `scripts/set_webhook.py` ставит вебхук на `https://<railway>/tg/webhook`.
4. Vercel: проект из `apps/web`, root directory, переменные `VITE_API_URL`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`. CORS на API — только домен Vercel и localhost.
5. Чек-лист после деплоя: `/health` ok, логин инспектора работает, бот отвечает на `/start`, `scripts/e2e_smoke.py --base-url <prod>` проходит.
Используй CLI (`vercel`, `railway`, `supabase`), где возможно, но все шаги, требующие моего аккаунта/логина, **явно попроси меня выполнить** и дай точные команды — не пытайся обойти авторизацию.

## 3. Модель данных

**Parcel (участок):** `id`, `cadastral_number` (формат РК, напр. `06:097:032:145`), `geometry` (MultiPolygon, SRID 4326, GiST-индекс), `centroid`, `area_ha` (считать через `ST_Area(geometry::geography)`), `purpose` (ИЖС, с/х, коммерция, промышленность, ЛПХ), `owner_type` (частная / аренда / гос), `address`, `lease_until`, `district`, `status`, `violation_type`, `deadline_at`, `inspector_id`, `updated_at`.
- `status`: `OK` (зелёный) · `UNDER_CHECK` (жёлтый) · `VIOLATION` (красный) · `IN_REMEDIATION` (красный, пунктирная обводка) · `RESOLVED` (зелёный) · `RETURNED_TO_STATE` (серо-синий).
- `violation_type`: `UNUSED`, `SELF_SEIZURE`, `DUMP`, `MISUSE`.

**StatusTransition** — журнал аудита: `entity_type`, `entity_id`, `from`, `to`, `actor`, `comment`, `created_at`. Разрешённые переходы — **явная машина состояний** в одном модуле; недопустимый переход → 409. Цикл по ТЗ: `VIOLATION → IN_REMEDIATION → RESOLVED | RETURNED_TO_STATE`; плюс `OK/UNDER_CHECK → VIOLATION`, `UNDER_CHECK → OK`.

**Signal («Народный контроль»):** `id`, `tracking_code` (`SIG-2026-0001`), `location` (Point, GiST), `category`, `description`, `status` (`NEW → IN_REVIEW → CONFIRMED | REJECTED`), `parcel_id` (автопривязка `ST_Contains`, иначе ближайший в 100 м через `ST_DWithin` на geography), `duplicate_of`, `reporter_chat_id`, `reporter_lang`, `created_at`.
- Сигнал внутри участка со статусом `OK` → участок автоматически `UNDER_CHECK`.
- Дедупликация: сигнал в радиусе 30 м за 7 дней → связать как дубликат, показывать «N жителей сообщили».

**Photo:** `id`, `owner_type (parcel|signal)`, `owner_id`, `storage_path`, `thumb_path`, `source (inspector|citizen)`, `taken_at`, `lat/lon` (EXIF), `uploaded_by`.

**Application (заявление):** `tracking_number` (`KZ-2026-042`), `applicant_name` (маскированное: «Ерлан С.»), `type`, `status` (`UNDER_REVIEW`, `INSPECTION_SCHEDULED`, `APPROVED`, `REJECTED`), `status_comment_ru`, `status_comment_kk`, `inspection_date`, `parcel_id?`, `history[]`.
**Subscription:** `chat_id`, `target_type (application|signal)`, `target_id`, `lang`.
**TelegramUser:** `chat_id`, `lang`, `created_at`, счётчики для rate-limit.
**Event:** `type` (`signal.created`, `parcel.status_changed`, …), `payload jsonb`, `created_at` — источник realtime.

## 4. Модуль 1 — Веб-панель инспектора

Дизайн: строгий «государственный», но современный; светлая тема по умолчанию + тёмная. Переключатель **RU / ҚАЗ** в шапке, все строки через i18next, никаких захардкоженных текстов. Логотип-заглушка с названием «ЖерБақылау».

**Вход:** страница логина (Supabase Auth, email+пароль), защищённые роуты. Демо-учётка из `.env`.

**Layout:** слева узкая навигация (Карта / Сигналы / Нарушения / Заявления / Дашборд), по центру полноэкранная карта, справа выезжающая карточка.

**Карта:**
- Полигоны по статусам (полупрозрачная заливка + чёткая обводка), hover-подсветка, тултип с кадастровым номером.
- Слой сигналов граждан: пульсирующий маркер для `NEW`, кластеризация при отдалении.
- Легенда со счётчиками, фильтры (статус, тип нарушения, назначение, «просрочен дедлайн»).
- Поиск по кадастровому номеру/адресу → `flyTo` и открытие карточки.
- Переключатель подложки OSM / Спутник.
- Слой «Спутниковый мониторинг (демо)»: раскраска NDVI по участкам из `SatelliteProvider`, подсветка кандидатов в «неиспользуемые». Явно подписан как демонстрация интеграции.
- **Realtime:** новый сигнал появляется без перезагрузки — анимация, toast «Новый сигнал SIG-2026-00XX» с кнопкой «Показать на карте», отключаемый звук. Цвет участка обновляется в реальном времени.

**Карточка участка:**
- Характеристики: кадастровый номер (копирование в 1 клик), назначение, площадь (га), адрес, тип владения, срок аренды.
- Статус-бейдж + **степпер жизненного цикла** «Выявлено нарушение → В процессе устранения → Устранено / Возвращено государству»; показываются только допустимые действия; каждое — модалка с обязательным комментарием.
- Фотогалерея с лайтбоксом, загрузка drag&drop (несколько фото, превью, прогресс), метки «инспектор / житель», дата, координаты.
- Дедлайн: date picker, обратный отсчёт («осталось 5 дн.» / красное «просрочено на 2 дн.»).
- Связанные сигналы и таймлайн истории изменений.
- «Сформировать акт (PDF)» — акт осмотра с реквизитами и фото (reportlab с кириллическим шрифтом, напр. DejaVu/Noto). Язык акта — выбранный язык интерфейса.

**Сигналы:** очередь (новые сверху), фото-превью, мини-карта, действия «Взять в работу» / «Подтвердить нарушение» (обновляет участок) / «Отклонить» (с причиной). Каждое действие уведомляет жителя в Telegram на его языке.

**Заявления:** таблица `KZ-...`, смена статуса с пояснением (RU и KZ) → push подписчикам в боте.

**Дашборд:** KPI (участки, нарушения, в работе, просрочено, сигналы за 7 дней, среднее время реакции), график сигналов по дням, распределение по типам нарушений, ближайшие дедлайны.

**UX-качество:** skeleton-загрузки, пустые состояния, понятные ошибки, адаптив под планшет.

## 5. Модуль 2 — Telegram-бот

Правило: пользователь **не набирает команд**, кроме `/start`. Всё — кнопки.

**При первом `/start`** — выбор языка: `🇰🇿 Қазақша` / `🇷🇺 Русский`; сохраняется в `TelegramUser.lang`, смена в «Помощь/Настройки». Все тексты — в файлах локализации (`apps/api/bot/locales/ru.ftl`, `kk.ftl` через aiogram-i18n/Fluent, либо YAML). Уведомления жителю — на его языке.

**Главное меню (reply keyboard):** `📄 Статус заявления` · `📚 Как оформить` · `📍 Сообщить о нарушении` · `🗂 Мои обращения` · `⚙️ Язык / Помощь`

**5.1 Статус заявления** — ввод трек-номера с примером; нормализация (`kz 2026 42` → `KZ-2026-042`); ответ-карточка: эмодзи-статус, этап, пояснение простым языком, дата, прогресс (`✅ Подано → ✅ Рассмотрение → ⏳ Выезд инспектора → ▫️ Решение`), что делать дальше; inline «🔔 Уведомлять об изменениях»; «не найдено» — дружелюбно с подсказкой.

**5.2 База знаний** — три процедуры: изменение целевого назначения; продление договора аренды; получение участка под ИЖС. Для каждой: пошаговая инструкция (листание «Далее/Назад»), чек-лист документов, сроки, госпошлина (если применимо), куда подавать, ссылка на egov.kz / акимат / Правительство для граждан. Контент — в `packages/seed/knowledge/{ru,kk}/*.md|yaml`, не в коде.
⚠️ Нормативку составь по Земельному кодексу РК и egov.kz, **не выдумывай номера статей**, в которых не уверен; в `docs/DECISIONS.md` пометь «требует сверки с актуальным регламентом». Казахские тексты пометь «требует вычитки носителем языка».
Кнопка «Не нашли ответ? Задать вопрос» → сохраняет вопрос.

**5.3 «Народный контроль» (FSM):**
1. Категория (свалка / заброшенный участок / самозахват / другое).
2. Геолокация: reply-кнопка `request_location=True`; также принимать точку, выбранную на карте во вложении. Проверка bbox региона.
3. Фото: 1–5 (в т.ч. альбомом и «файлом» без сжатия), кнопка «Готово»; скачивание через `getFile` → Supabase Storage.
4. Описание до 500 символов или «Пропустить».
5. Подтверждение: сводка (категория, адрес через обратное геокодирование Nominatim с кэшем, User-Agent и fallback на координаты; кол-во фото; текст) → «Отправить» / «Изменить» / «Отмена».
6. «Сигнал SIG-2026-00XX принят» + push на каждом изменении статуса.
- «Отмена» на любом шаге, таймаут FSM, rate limit (напр. не более 5 сигналов в час).
- Webhook-обработчик отвечает Telegram быстро; тяжёлую работу (скачивание фото, превью) — в фоне, чтобы не было повторной доставки апдейтов; обработка идемпотентна по `update_id`.

**5.4 Мои обращения** — сигналы пользователя и подписки на заявления со статусами.

## 6. Сквозной цикл (35% оценки) — реализовать и покрыть тестом

1. Житель завершает сценарий в боте → создаётся Signal, фото в Storage, привязка к участку через PostGIS, участок `OK → UNDER_CHECK`, аудит, запись в `events`.
2. Supabase Realtime → веб-панель: точка появляется, участок желтеет, toast.
3. Инспектор подтверждает → `VIOLATION` (красный), дедлайн, своё фото → `IN_REMEDIATION` → `RESOLVED`.
4. Notifier отправляет жителю сообщения в Telegram на его языке на каждом этапе.
5. Аналогично — смена статуса заявления `KZ-...` → push подписчикам.

`scripts/e2e_smoke.py --base-url ...` прогоняет цикл через API (сигнал эмулируется служебным эндпоинтом `POST /api/v1/dev/simulate-signal`, доступным только с сервисным ключом) и проверяет статусы и события. Работает и локально, и на проде.

## 7. Тестовые данные

Регион — **Жамбылская область, окрестности Тараза** (фиктивные правдоподобные координаты, ~42.90 N, 71.37 E и пригороды).
- 40–60 полигонов правдоподобной формы, кварталами, без пересечений (проверка `ST_IsValid` и отсутствия overlap в тесте). ИЖС 0.06–0.15 га, с/х 5–50 га.
- Статусы: ~60% зелёных, ~15% жёлтых, ~20% красных (разные типы, часть с просроченными дедлайнами), несколько «возвращено государству».
- 8–10 заявлений `KZ-2026-001 … KZ-2026-042` во всех статусах, с историей и пояснениями на RU и KZ (обязательно `KZ-2026-042`).
- 5–8 исторических сигналов с нейтральными сгенерированными фото-плейсхолдерами (без чужих фото из интернета).
- Данные в `packages/seed/`; сид идемпотентен; `make demo-reset` (и `python scripts/demo_reset.py` для Windows) возвращает БД в исходное состояние — работает и против прода.
- Если положу GeoJSON организаторов в `packages/seed/organizers/`, сид подхватит его с гибким маппингом полей.

## 9. Работа вдвоём

Раздели работу так, чтобы два человека с двумя Claude Code не конфликтовали:
- **Человек A (web):** `apps/web` — карта, карточка, сигналы, дашборд, i18n веба, деплой на Vercel.
- **Человек B (backend+bot):** `apps/api` — модели, API, бот, notifier, сид, Supabase, Railway.
- Фаза 0 и Фаза 1 (каркас + контракт API) делаются **первыми и вместе**; после мержа контракта — параллельная работа.
- Git: `main` защищённая; ветки `feat/web-*`, `feat/api-*`; маленькие PR; сгенерированные типы API коммитятся, чтобы фронт не зависел от запущенного бэкенда.
- Пропиши это в `CLAUDE.md`, чтобы каждый Claude Code знал зону ответственности своего человека и не трогал чужие папки без необходимости.

## 12. Чего НЕ делать

- Не хранить координаты вне PostGIS; не использовать SQLite.
- Не запускать бота как serverless-функцию на Vercel.
- Не класть service role key / токен бота во фронтенд или в git.
- Не хардкодить тексты (веб и бот — только через локализацию), не хардкодить нормативку в коде.
- Не оставлять неработающих кнопок; незаконченное — не показывать.
- Не выдумывать реальные ПДн, реальные кадастровые номера людей и неподтверждённые ссылки на статьи закона.
- Не усложнять: без Kubernetes и лишних микросервисов.
